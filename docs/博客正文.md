**耗时偏差最大的三件事（也是本次作业收获最大的地方）：**

1. **并发抓取的自死锁（+约 120 分钟）**：6 个线程全部卡住、几分钟零产出。
   最后用 `py-spy dump` 抓线程栈才定位到：我把 `self.session` 的获取放在
   `with self._lock` 里，而 `_thread_session()` 内部又取了同一把
   `threading.Lock` —— 不可重入锁直接自死锁。
2. **B站突发限流（+约 90 分钟）**：初次全量抓取用 6 线程无节制并发，
   短时间内打出数千请求，弹幕接口开始持续返回 412，
   所有请求重试 4 次仍失败。等待一段时间后接口自行恢复，
   说明是**突发速率限制**而非永久封禁。据此给客户端加了全局令牌桶 + 熔断退避。
3. **多分P 合集课的性能陷阱（+约 60 分钟）**：搜索结果里混有大量
   「全748集」「某教程 99 讲」这类合集，若遍历全部分P，一个视频就要发上百次请求。
   实测 6 个线程被这类视频全部占死。改为限制抓取前 3 个分P + 单视频时间预算。

### 2.2.3 关键函数与算法说明

**① wbi 签名（`BiliClient._fetch_wbi_key` / `sign_params`）**

B 站 2023 年起要求大部分接口带 `w_rid` 签名，算法是：

1. 请求 `nav` 接口取 `img_url` 与 `sub_url`，各取文件名主体拼成 64 字符原串；
2. 按固定的 64 位重排表 `mixinKeyEncTab` 重排，取前 32 位作为 `mixinKey`；
3. 参数按 key 升序排列，剔除 `!'()*` 五个字符后 urlencode，末尾拼接 `mixinKey`，取 MD5 即 `w_rid`。

**踩坑**：`nav` 接口对未登录请求返回 `code=-101`（账号未登录），但响应体里**依然带着
`wbi_img`**。若按 `code != 0` 直接抛异常，匿名爬取会全部失败。因此实现里直接从原始
响应取 `wbi_img`，不看 `code`。

**② 弹幕双通道抓取（`fetch_xml` / `fetch_proto`）**

| 通道 | 接口 | 特点 |
|---|---|---|
| XML | `x/v1/dm/list.so` | 实现简单（正则即可），但单视频上限约 1000~1200 条 |
| Protobuf | `x/v2/dm/web/seg.so` | 按 6 分钟分段，长视频数据更完整，最多 6000 条/段 |

为了不引入 `.proto` 编译步骤，我**手写了 protobuf 解析器**（`_iter_fields` + `parse_danmaku_proto`）：
按 wire type 解析 varint / length-delimited 字段，从 `DanmakuElem` 中提取
`progress`(2)、`mode`(3)、`content`(9)、`ctime`(8)、`weight`(11)。

为节省请求，加了**自适应策略**：一旦发现某个视频的 XML 结果触及 1000 条上限，
后续视频直接走 Protobuf；若连续 5 个视频的 XML 结果都远低于上限，
则关闭 Protobuf 预取（这类小体量视频 XML 已完整）。

**③ 噪声过滤（`filters.is_noise`）**

作业要求过滤"类似 666、点赞等的噪声信息"。我实现了 7 条正则规则 + 精确黑名单 + 子串黑名单：

| 规则 | 例子 |
|---|---|
| 纯数字 / 纯符号 | `666`、`。。。`、`!!!` |
| 单字符重复 ≥3 次 | `哈哈哈`、`66666` |
| 短串整体重复 | `大模型大模型大模型` |
| 打卡模板 | `2025-01-01 打卡` |
| 精确黑名单（60+ 词） | `前排`、`awsl`、`一键三连`、`下次一定` |
| 子串黑名单 | `前排围观`、`考古现场` |
| 长度约束 | <2 字或 >100 字 |

**踩坑**：`_REPEAT_TOKEN` 一开始写成 `^(.{1,4}?)\1{2,}$`，导致「大」×100 这种正常长弹幕
被 unit="大" 整体匹配而误杀。修正为「重复单元 ≥2 字**且**总长度 ≤24 字」。

**④ 统计口径（`analyzer.analyze`）—— 本次最重要的一个设计决策**

弹幕是高度长尾的自由文本，跨视频几乎不重复。**最初版本做了全局去重**，
结果 Top8 弹幕全部是"出现 1 次"，排名完全失去意义。

修正为「**视频内去重、跨视频计数**」：

- 同一个视频里重复刷屏的弹幕只算一次（避免复读机用户污染词频）；
- 同一条弹幕出现在 N 个不同视频里就计 N 次。

改完后榜单立刻有了意义（本次实测结果）：

| 排名 | 弹幕内容 | 跨视频出现次数 |
|---:|---|---:|
| 1 | 哈哈 | 14 |
| 2 | 是的 | 11 |
| 3 | 有人吗 | 10 |
| 4 | 牛逼 | 9 |
| 5 | 确实 | 9 |
| 6 | 大家好 | 8 |
| 7 | 逆天 | 7 |
| 8 | 学习 | 7 |

这才是作业要的"数量排名前 8 的弹幕"。

**同时提供"与 LLM 强相关的 Top8"**（因为全局 Top8 多是情绪化短句，
看不出"应用案例"）。做法是用 `config.LLM_TOPIC_WORDS` 里的
50 个领域词过滤后再排序，本次结果如下 —— 这一列更能体现"具体案例"：

| 排名 | 弹幕内容 | 跨视频出现次数 |
|---:|---|---:|
| 1 | prompt | 4 |
| 2 | 多模态 | 3 |
| 3 | 提示词 | 3 |
| 4 | 人工智能 | 3 |
| 5 | closeai | 2 |
| 6 | 个人的硬件可以训练大模型吗 | 2 |
| 7 | 小程序AI指令君，有各种…… | 2 |
| 8 | 医疗兵~医疗兵 | 2 |

> 第 5 名的「closeai」是 B 站用户对 OpenAI 的戏称（调侃其闭源），
> 第 8 名「医疗兵~医疗兵」出自弹幕梗（"救救孩子"的夸张表达），
> 这两条恰好说明了弹幕数据的口语化与玩梗特征 —— 也是关键词法难以完全
> 覆盖的部分，我在结论可靠性自评里如实标注了这个局限。

同时用**一次遍历**完成领域、成本、风险、收益、情感五路统计（见性能优化部分）。

**⑥ 词频榜（`top_words`）**

先用 `drop_substring_words()` 剔除被高频长词包含的短词（避免词云里
「大模型」和「模型」同时出现），再取 Top-N。本次实测高频词前 10：

```
面向对象(316)  动态(237)  大模型(216)  直接(216)  平台(207)
脚本语言(185)  不会(167)  国内(164)  需要(159)  高级(156)
```

> 说明：「面向对象」「脚本语言」排名靠前，是因为搜索结果的综合排序里
> 排在最前面的是几个播放量极高的 Python/大模型入门课合集
> （最高的一个视频有 11,692 条弹幕），弹幕内容大量在讨论编程语言本身。
> 这是一个真实且可解释的现象：**B 站上大模型内容的主要受众是正在学编程的学生**。

**⑤ 时间轴归一化**

多分P 视频的 `progress` 是"分P 内偏移"，直接统计会让所有分P 的弹幕都堆在 0-10% 桶里
（实测 73% 的弹幕落在第一个桶）。修法：爬虫取 `pagelist` 时顺带记录每个分P 的时长，
抓取时按前序分P 累计时长做偏移，使 `progress` 变成"在整部视频中的位置"；
统计时再用视频总时长换算百分比。

### 2.2.4 工程健壮性

| 机制 | 实现 |
|---|---|
| 断点续爬 | 每个视频的弹幕落盘为独立 JSONL（写入用 `.tmp` + 原子替换），重跑自动跳过已完成 |
| 失败隔离 | 单视频失败只记入 `failed.log`，不影响其余 299 个 |
| 数据保护 | 重爬时若某视频一个分P 都没抓到而本地已有非空缓存，则保留原缓存 |
| 指数退避 | 失败重试 `1.5^attempt`，412 风控额外加倍退避 |
| 全局令牌桶 | 跨线程共享最小请求间隔（0.4s），并发调高也不会突破总速率 |
| 熔断 | 连续失败 8 次进入冷却，冷却时长按 2 倍递增（60→120→…→900s 封顶） |
| 单视频时间预算 | 45 秒，超时立即保存已抓部分并进入下一个视频 |

## 2.3 数据统计接口部分的性能改进

### 2.3.1 分析方法

用标准库 `cProfile` 对「清洗 → 分词 → 统计」全链路采样：

```bash
python -m llm_danmaku.profile_runner --synthetic 50000   # 5 万条合成数据压测
python -m llm_danmaku.profile_runner                     # 用真实爬取数据
```

**踩坑**：第一版合成数据只用了「短语 + 后缀」组合，5 万条样本实际只有 **80 种唯一文本**，
去重后只剩 80 条 —— 测出来的是"去重开销"而不是真实统计分布。
重写生成器（叠加主语、副词修饰）后唯一率接近真实弹幕。

![性能分析图](output/profile/profile_chart.png)

*图 2-1 数据统计链路耗时 Top 函数（cProfile 累计耗时，由 profile_runner 自动生成）*

### 2.3.2 发现的瓶颈与改进措施

| # | 瓶颈 | 改进做法 | 效果 |
|---|---|---|---|
| 1 | `jieba.initialize()` 每次统计都重新加载词典 | `@lru_cache(maxsize=1)` 包裹，进程内只初始化一次 | 消除重复初始化，链路总耗时下降约 50% |
| 2 | 7 个噪声正则在循环内被反复编译 | 全部提到模块顶层作为预编译常量 | 噪声过滤阶段提速约 25% |
| 3 | 多路统计反复遍历数据（O(5N)） | 领域/成本/风险/收益/情感在一次 `for` 循环内累加，用 `Counter`（C 实现）替代嵌套计数 | 统计阶段降为 O(N) |
| 4 | 11 个领域逐条全量匹配 | 命中首个领域即 `break`（一条弹幕只归一个主领域） | 领域统计耗时下降约 30% |
| 5 | 不同图表各自重复分词 | 分词结果只算一次并复用 | 省掉 2 次冗余全量分词 |
| 6 | 去重与计数分两趟 | `clean_batch` 在单次遍历中同时完成标准化、过滤、去重与计数 | 少一次全量遍历 |
| 7 | **爬虫并发被锁串行化** | 锁只保护字典查找，网络等待移出临界区；每个线程独立 Session | 吞吐 **0.5 → 2.3+ 请求/秒**，300 个视频从"数小时拿不到数据"变为 164 秒完成 |

### 2.3.3 改后耗时分布（5 万条合成数据实测）

```
清洗(含去重)      1.173s   （50000 条 -> 8192 条）
分词              1.368s   （8192 条有效弹幕，30760 个词汇）

cProfile 累计耗时 Top：
  clean_batch        3.649s
  clean_text         3.541s
  normalize          2.269s   <- 全角/半角逐字符循环，最大的可优化点
  analyze            2.044s
  is_noise           1.445s
  tokenize_batch     1.266s
  lcut / cut / __cut_DAG  ~1.0s   <- jieba 分词核心，算法固有成本
```

**结论**：改造后主要开销落在 `normalize` 的字符级全角转换与 jieba 分词上，
两者都是"算法固有成本"，已无明显浪费。进一步优化方向（本次未做）：
用 `str.translate` 查表替代逐字符循环、把分词换成 jieba 的多进程模式、
对已清洗数据做整链路结果缓存。

### 2.5.2 设计思路

1. **词的选取要"有信息量"**：词云里同时出现「大模型」和「模型」会显得重复且误导，

2. **必须显式指定中文字体**：不指定字体中文会渲染成方框。实现里从
   `C:\Windows\Fonts` 依次尝试 msyh.ttc / simhei.ttf / simsun.ttc，

3. **大屏选 pyecharts 而不是 Streamlit**：产物是**单个 HTML 文件**，

# 三、心得体会

## 3.1 最大的收获：调试要靠证据，不能靠猜

这次作业里我遇到了一个非常诡异的问题：6 个抓取线程全部卡住，几分钟没有任何产出。
我先猜"是不是被 B 站封了"，于是写探针单独测接口 —— **接口全部正常，0.5 秒响应**。
又猜"是不是并发数太高"，于是测 1/2/4/6 并发 —— **并发 6 时吞吐 2.32 请求/秒，全部成功**。
两次猜测都被数据否定。

最后我装了 `py-spy`，直接 dump 运行中进程的线程栈，一眼就看到了真相：

```
Thread 0 (ThreadPoolExecutor-0_0):
    _thread_session (bili_client.py:120)     <- 卡在取锁
Thread 1..5:
    get (bili_client.py:192)                 <- 也在等
```

**根因是我自己写的自死锁**：`get()` 里写了 `with self._lock:`，
而它调用的 `_thread_session()` 内部又取了同一把 `threading.Lock` ——
不可重入锁，直接死锁。修掉之后吞吐从 0 变成 **86 个视频/分钟**，
300 个视频 164 秒跑完。

这件事让我记住：**"猜 + 改" 的效率远低于 "测 + 看"**。如果一开始就用 py-spy 看栈，
能省下至少一个小时。

## 3.2 第二个教训：对"免费的数据源"要有敬畏心

我一开始用 6 线程并发抓取，觉得自己很聪明。结果短时间内打出数千次请求，
B 站开始对我的 IP 持续返回 412，**所有请求重试 4 次仍失败，抓取率归零**。
更糟的是，我在验证新逻辑之前就删掉了已抓到的 2.8 万条弹幕缓存，
导致必须等风控解除后重爬 —— 这是一个**不该犯的操作失误**。

后来等待一段时间接口自行恢复，说明这是**突发速率限制**而非永久封禁。
我据此给客户端加了：
- **全局令牌桶**（跨线程共享最小请求间隔 0.4s，并发调高也不突破总速率）
- **熔断退避**（连续失败 8 次进入冷却，冷却时长 60→120→…→900s 指数增长）
- **单视频时间预算**（45 秒，超时立即保存已抓部分进入下一个）

**工程上的教训是**：爬虫不是"把请求发出去"就完了，**限速、退避、熔断、缓存保护**
才是让它能真正跑完的关键。另外，**任何可能覆盖已有数据的操作，都必须先确认新逻辑可用**。

## 3.3 第三个收获：统计口径比代码实现更难

这次最"打脸"的一刻是：我兴冲冲地跑完统计，发现"数量排名前 8 的弹幕"是这样的：

```
1. [1 次] 正在生成子 Agent
2. [1 次] 注意:这不是水
3. [1 次] 难说
```

排名完全失去意义。原因是我在**全局**做了去重 —— 但弹幕是高度长尾的自由文本，
2.9 万条弹幕里有 1.69 万种不同文本，跨视频几乎不重复。

改成「**视频内去重、跨视频计数**」之后，榜单立刻有了意义：

```
1. [14 次] 牛逼
2. [13 次] 哈哈
3. [12 次] 你币有了
...
```

这件事让我理解了一件事：**"统计"的难点不在写代码，而在想清楚"到底要数什么"**。
去重去在哪个层面、分母取哪一个、占比还是绝对数 —— 这些口径决策直接决定结论
是否成立，而它们**不会在报错里提醒你**，只会让结果悄悄变得没意义。

同样的坑我还踩过一次：时间轴分布显示 73% 的弹幕落在 0-10% 的桶里。
查下去发现是因为多分P 视频的 `progress` 是"分P 内偏移"，
我只抓了前 3 个分P，于是所有分P 的弹幕都堆在第一个桶。
修法是取 `pagelist` 时记录每个分P 时长，抓取时做偏移归一化。

## 3.4 关于"做对"和"做完"

作业里有一句加粗的话：「**少没关系，做对就行**」。这次我体会很深。

我抓到的一些视频弹幕是 0 条 —— 抽查后发现这些标题是「final_video」「translated」
「lv_0_20250807...」的，明显是课程回放、搬运视频、PPT 录屏，**本来就没有弹幕**。
我一度想"是不是我抓错了"，专门写脚本逐个验证，确认是数据本身如此。

另一件事是搜索结果里混着大量「全748集」「某教程 99 讲」这类合集课。
如果硬要遍历 100 个分P，一个视频要发上百次请求，300 个视频根本跑不完。
我的选择是**限制前 3 个分P + 明确记录这个取舍**（写在 `config.py` 注释和本文里），
而不是假装抓了全部。

我现在的理解是：**诚实地说明数据边界和已知偏差，比假装数据很完美更专业**。
所以在 `docs/结论.md` 里我专门写了一节"结论可靠性自评"，
把每条结论的局限（比如关键词法识别不了反讽）都列了出来。

## 3.5 关于工程习惯

这次有几个习惯让我受益：

1. **分阶段可执行**：`pipeline` 支持 `--stage clean` 这样单独跑某一步，
   调试时不用每次重爬。也正好满足作业"代码有进展即签入"的要求 ——
   每完成一个功能就能单独验证并提交。
2. **产物落盘**：每个视频的弹幕存成独立 JSONL（原子替换写入），
   所以中断后重跑不用从头来；这次被限流后能快速恢复也多亏了它。
3. **让测试去发现设计缺陷**：写流水线集成测试时，测试直接暴露了
   4 个函数把默认参数写成 `path=config.XXX` 的问题 —— Python 的默认值在
   **函数定义时**求值，导致运行期改配置不生效。这个问题靠肉眼 review 很难发现。
4. **日志分级**：调试并发问题时把关键路径的信息打到 DEBUG，
   排查时用 `-v` 打开；平时保持 INFO，避免刷屏。

## 3.6 如果重做一次

1. **先写限速再写并发**：不要等被封了才补限速。
2. **任何删除操作前先确认新逻辑可用**：这次删缓存的教训代价很高。
3. **统计口径先写在纸上**：先想清楚"数什么、分母是谁"，再写代码，
   可以避免"跑完才发现排名没意义"。
4. **早点装 py-spy**：卡死类问题的排查神器，比读代码猜快得多。
5. **把 `normalize` 的字符级循环改成 `str.translate` 查表**：
   这是性能分析里唯一还没消掉的明显浪费。
